### C. 排查直播横屏卡顿

**症状**：进入直播间 → 切横屏 → 大约几秒后整个直播画面卡住 3–4 秒 → 自行恢复；刷新直播源后必定复现。

**已经排除的**

1. **不是 Activity 重建**：`AndroidManifest.xml` 的 `configChanges` 已包含 `orientation|keyboardHidden|screenSize|smallestScreenSize|screenLayout|density`，旋转不会销毁重建 Activity。
2. **不是旋转触发重连**：`live_player_page.dart:304 _toggleOrientation()` 只调 `SystemChrome.setPreferredOrientations` 和 `setEnabledSystemUIMode`，没有重建 `DualLiveSession` 或 `Player`。

**可疑点，按可能性排序**

1. **Video 控件在布局分支里被重建**
   `live_player_page.dart:578` 用 `_landscape` 切两套布局，而 `_buildVideo()` 有两个调用点（613、645）。切分支时 `Video`/`Texture` 在 Element 树里的位置变化，没有 `GlobalKey` 会走销毁重建，纹理重新绑定、mpv VO 重新初始化，表现就是画面停住几秒。
   → 验证：给视频层套固定 `GlobalKey`，或把树结构固定成「外层尺寸变、内层不变」。
2. **缓存窗口太大**
   `live_leg.dart:81-83` 设了 `cache-secs=40`、`demuxer-readahead-secs=40`。一旦卡住要重新填满 40 秒的缓存窗口，恢复慢与 3–4 秒吻合；1080p 下 40 秒缓存的内存占用也偏高。
   → 验证：临时改成 8–15 秒，对比卡顿恢复时间。
3. **渲染面积变大 + 弹幕叠加**
   横屏后渲染像素翻倍，如果同时在跑双路解码，GPU 可能掉帧。
   → 验证：关掉声音源只留单路，看是否还卡。
4. **双路带宽竞争**
   画面 + 声音两路同时拉流，横屏时若第二路正在补缓存，会抢占带宽。
   → 验证：临时只用官方声音（单路），观察是否复现。

**排查手段**

- 现成打点已在：`[LumiPlayer] orientation -> landscape platform calls Xms` 与 `orientation first frame in Xms`，先看旋转本身耗时多少
- 补三个打点：`buffering` 开始/结束时间、`player.state.position` 是否停住、`cache-secs` 与实际缓存时长（`demuxer-cache-time`）
- 抓日志：`adb logcat | grep -i LumiPlayer`
- 对比实验顺序：**先验证可疑点 1**（成本最低、最符合"必现"特征），再调缓存
